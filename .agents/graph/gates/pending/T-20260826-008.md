# Gate: T-20260826-008 — Alta de staff: administrativo puede crear cuentas (antes owner-only)

- severity: high (crea cuentas reales de Supabase Auth, ampliando quién puede hacerlo — mismo nivel que T-20260821-007/T-20260825-002)
- approval_mode: sync
- created: 2026-08-26

## Qué se hizo

`app/api/v1/staff/route.ts`, `POST`: `requireRole(context, ["owner"])` → `requireRole(context, ["owner", "staff"])` + un segundo gate explícito para `staff`: `resolveOwnStaffMember(context)` debe devolver `staffCategory === "administrative"`, si no tira `ForbiddenError`. `requireRole()` por sí solo no puede expresar "staff, pero solo esta categoría" — solo conoce `role`.

- `lib/staff/resolve-own-staff-member.ts` (nuevo) — resuelve la fila `staff_members` propia del caller (`users.authUserId = context.userId` → `staffMembers.userId`). Compartido con T-20260826-007, que antes tenía esta misma query duplicada inline en `staff/me/attendance/route.ts` — refactorizado para usar el helper nuevo, sin cambio de comportamiento ahí.
- Resto del `POST` (creación real vía `admin.auth.admin.createUser`, patrón transaccional-con-compensación) sin cambios — solo se amplió quién llega a ejecutarlo.

## Por qué requiere revisión (síncrona, no async)

- **Amplía quién puede crear cuentas reales de Supabase Auth** — mismo tier de riesgo que T-20260821-007 (creación de cuentas) y T-20260825-002 (quién define la contraseña). No es un cambio de UI ni de lectura: cada llamada exitosa crea un usuario real en Auth con acceso al sistema.
- Decisión de negocio ya confirmada por el usuario en `tasks.md` antes de este `#run` (administrativo puede dar de alta cualquier categoría, incluido otro administrativo) — lo que faltaba era la aprobación explícita de ejecutar el cambio de código en sí, según `policy.yml` (`high` = `approval_mode: sync`, bloquea hasta aprobación explícita, `requires_named_approver: true`).
- **Aprobado por SudacaDev vía `AskUserQuestion` en esta misma sesión (2026-08-26)**, antes de escribir el código — no después. Pregunta exacta: si confirmaba correr T-008 tal como está descripta en `tasks.md` (administrativo puede crear cualquier categoría). Respuesta: "Sí, correla".

## Gap deliberadamente no resuelto en esta tarea

Esto solo amplía el endpoint `POST`. `GET /api/v1/staff` (roster) y el link "Equipo" del nav siguen owner-only (T-20260825-001) — un administrativo puede llamar este `POST` directo (ej. vía herramientas de desarrollo o una futura pantalla propia), pero hoy no tiene ningún botón "Invitar" visible en la UI para llegar a él. No se tocó a propósito: es exactamente el tipo de permiso "rol+categoría" que **T-20260826-014** reserva para su propia discusión (recomienda convocar `backend-developer` antes de tocarlo) — abrir la visibilidad de GET/nav acá hubiera sido asumir esa decisión de modelo de permisos sin que el usuario la haya tomado todavía para ese eje específico.
