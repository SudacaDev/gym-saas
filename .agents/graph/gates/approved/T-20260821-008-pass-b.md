## Por qué requiere revisión

- Migración de schema que **borra una columna real con datos** (`activity_name`, texto libre usado como nombre de actividad hasta ahora) — irreversible sin restaurar desde backup, a diferencia de pass A que era puramente aditiva.
- Endurece `activity_id` a `NOT NULL`: si alguna fila real quedó sin backfillear entre pass A y ahora (por un alta manual fuera de la app, por ejemplo), la migración fallaría en `ALTER COLUMN ... SET NOT NULL` — comportamiento seguro (falla en vez de corromper datos), pero vale que quede explícito acá.
- Mismo patrón de severidad que T-003/T-005/T-008-pass-A: cambio de schema contra producción, gate síncrono con aprobador nombrado.

## Qué opciones se consideraron

1. **Backfill defensivo antes del `NOT NULL`** (un `UPDATE ... WHERE activity_id IS NULL` con algún valor placeholder): descartado — no hay ningún valor de placeholder razonable para una FK a `activities`, y si hay filas sin backfillear es una señal de que algo salió mal en pass A que hay que investigar, no encubrir con un placeholder.
2. **Mantener `activity_name` como columna espejo (no borrarla)**: descartado — el propósito completo de esta tarea era reemplazar el texto libre por la FK; dejar la columna vieja sin usar es deuda que nadie pidió.

## Resultado (intento 1, 2026-08-24)

`npm run db:migrate` falló **antes de ejecutar ningún DDL propio** — ningún `ALTER TABLE` de `0007_many_silver_surfer.sql` llegó a correr. La falla es de infraestructura, no de la migración:

```
PostgresError: remaining connection slots are reserved for roles with the SUPERUSER attribute
severity: FATAL, code: 53300, routine: InitPostgres
```

Diagnosticado corriendo `drizzle-orm/postgres-js/migrator` directo (bypaseando el CLI de `drizzle-kit`, que no imprimía el error real detrás del spinner) — la conexión a la base falló al abrir la sesión, antes de `CREATE SCHEMA IF NOT EXISTS "drizzle"` (el primer statement interno de drizzle-kit, ni siquiera parte de esta migración). Base sin tocar, sin riesgo de estado parcial.

Causa probable: el pool de conexiones de la base real está saturado (límite de conexiones del lado de Postgres/Supabase, código `53300` = "conexiones reservadas para superusuario"). No es algo que este intento de migración haya causado por sí solo — puede deberse a otro proceso local (`next dev` u otro cliente) sosteniendo conexiones abiertas, o al pool del proveedor saturado por motivos externos a esta sesión.

**No se reintentó automáticamente** — insistir contra un pool ya saturado no ayuda y agrega presión. Reportado al usuario, esperando que libere conexiones (parar cualquier `next dev`/cliente de DB corriendo, o esperar a que el proveedor libere el pool) antes de un segundo intento.

## Resultado (intento 2, 2026-08-24)

El usuario pidió reintentar (`correlo vos al migrate`). El error de conexión ya no apareció, pero `npm run db:migrate` volvió a fallar — esta vez el CLI de `drizzle-kit` volvía a tragarse el error real detrás del spinner, así que se corrió `drizzle-orm/postgres-js/migrator` directo (bypaseando el CLI) para verlo:

```
PostgresError: column "activity_id" of relation "class_schedules" contains null values
code: 23502 (not-null violation)
```

Un `SELECT` de solo lectura confirmó la causa: **4 filas reales** de `class_schedules` (todas `activity_name = 'indoor cycling'`, creadas el 2026-08-22T16:29:58Z) tenían `activity_id IS NULL`. No es un error de esta migración ni de pass A — esas filas se crearon **después** de que pass A verificara "0 filas sin asignar", usando la API vieja de ese momento (que todavía solo guardaba `activity_name`, sin tocar `activity_id`). Nadie mintió en ningún gate anterior; el estado de la base simplemente siguió avanzando entre pass A y pass B porque la app se siguió usando.

Reportado al usuario con el detalle exacto (las 4 filas, la fecha, la causa) y una propuesta de backfill puntual — misma lógica que el backfill original de pass A (`INSERT ... SELECT DISTINCT` + `UPDATE ... FROM`), acotada con `WHERE activity_id IS NULL` para no tocar las 6 filas ya correctas. Aprobado por el usuario vía `AskUserQuestion` ("Sí, backfill + migrar").

**Backfill ejecutado** (transacción única, vía script disponible solo durante esta ejecución, no committeado — ver nota abajo):
```sql
INSERT INTO "activities" ("tenant_id", "name")
SELECT DISTINCT "tenant_id", "activity_name" FROM "class_schedules"
WHERE "activity_id" IS NULL
ON CONFLICT ("tenant_id", "name") DO NOTHING;
-- → 1 fila insertada: "indoor cycling" (tenant bd15902e-c6e6-4e76-aa33-170e3bc5c106)

UPDATE "class_schedules" cs
SET "activity_id" = a."id"
FROM "activities" a
WHERE a."tenant_id" = cs."tenant_id" AND a."name" = cs."activity_name" AND cs."activity_id" IS NULL;
-- → 4 filas actualizadas
```
Verificado: 0 filas con `activity_id IS NULL` después del backfill.

**Migración aplicada** inmediatamente después (`ALTER COLUMN activity_id SET NOT NULL` + `DROP COLUMN activity_name`), seguida de `apply-policies.ts` (4 archivos, idempotente, sin cambios — pass A ya había dejado las policies de `activities`/`class_schedules` correctas).

**Verificación final contra la base real:**
- `class_schedules`: 8 columnas, `activity_name` ya no existe, `activity_id` es `uuid NOT NULL`.
- 10 filas reales (6 originales + las 4 de "indoor cycling" backfillleadas) joinean correctamente contra `activities` — ningún dato se perdió.
- `relrowsecurity`/`relforcerowsecurity` en `true` para `activities` y `class_schedules`.
