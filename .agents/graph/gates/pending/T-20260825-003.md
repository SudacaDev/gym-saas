## Qué se hizo

Ya hecho, es local y no toca la base real (revertible con `git restore`/`git clean`):

- `db/schema/members.ts` — columna nueva `short_code` (`text`, **NOT NULL**), con `uniqueIndex("members_tenant_id_short_code_unique")` sobre `(tenant_id, short_code)` — único **por tenant**, no global (ver "Decisiones tomadas" abajo).
- `db/migrations/0010_known_mordo.sql` — generado con `npm run db:generate` (`drizzle-kit generate`, sin conexión a la DB) y **editado a mano después** para intercalar el backfill: 1) `ADD COLUMN short_code` nullable, 2) bloque `DO $$ ... $$` que recorre cada fila existente de `members` y le asigna un código candidato con el formato acordado (2 letras + 2 dígitos + 2 letras), reintentando en un loop interno hasta encontrar uno libre dentro del mismo `tenant_id`, 3) `ALTER COLUMN short_code SET NOT NULL`, 4) `CREATE UNIQUE INDEX`. Mismo patrón que el backfill de `class_schedules.activity_id` en `db/migrations/0006_quiet_bedlam.sql` (T-20260821-008, pass A) — ver ese gate para la referencia. Acá se resolvió en un solo pass (no dos, como en T-008) porque no hay tabla catálogo que poblar primero, solo un valor random por fila.
- `lib/members/generate-short-code.ts` (nuevo) — `generateShortCode()`: un candidato en el formato acordado (2 letras + 2 dígitos + 2 letras, ej. "AB12CD"). No garantiza unicidad por sí sola — la unicidad la fuerza el índice único de la DB; el llamador reintenta.
- `lib/api/handle-api-error.ts` — agregado `isUniqueViolation(error, constraintName?)`, mismo patrón que el `isForeignKeyViolation` ya existente (unwrap de `.cause` para el `DrizzleQueryError`, chequeo de SQLSTATE — acá `23505` en vez de `23503`), con chequeo opcional de `constraint_name` para no capturar cualquier unique violation de la tabla, solo la del short code.
- `app/api/v1/members/route.ts` (`POST`) — genera un `shortCode` candidato, intenta el insert; si choca contra `members_tenant_id_short_code_unique` reintenta hasta 5 veces (`SHORT_CODE_MAX_ATTEMPTS`) con un candidato nuevo cada vez; si agota los intentos, responde `503` con mensaje claro en vez de un 500 genérico. Con 26×26×10×10×26×26 ≈ 45.7M combinaciones por tenant, este camino de reintento debería ser prácticamente inalcanzable en la práctica — se implementó de todos modos por prolijidad defensiva, no porque se espere que dispare.
- Display: `features/checkin-page/index.tsx` — el código corto se muestra como label secundario (mono, chico, `text-muted-foreground`) al lado del nombre en la lista principal, y también en el panel "En el gym ahora". La búsqueda del buscador ahora también matchea por `shortCode` (útil en el mostrador: alguien puede tipear el código en vez de buscar por nombre). `features/members-page/index.tsx` — columna nueva "Código" en la tabla de socios. `features/member-detail-page/index.tsx` — nuevo campo "Código" en la lista de datos de la ficha del socio, arriba del email (es parte de la identidad del socio, mismo criterio que el resto de esa lista).
- Tests actualizados para que sigan compilando/corriendo con la columna nueva `NOT NULL`: `tests/unit/checkin-checkout.test.ts`, `tests/unit/checkin-requires-active-membership.test.ts`, `tests/unit/member-soft-delete.test.ts`, `tests/unit/dashboard-metrics.test.ts`, `tests/unit/payment-extends-membership.test.ts`, `tests/integration/tenant-isolation/rls-policies.test.ts` — todos los `insert(schema.members)` ahora pasan `shortCode` (la mayoría vía `generateShortCode()`, reusando el mismo generador que usa la app real en vez de reinventar uno de prueba).

Falta ejecutar: `npm run db:migrate`.

## Decisiones tomadas (no re-abiertas, ya confirmadas con el usuario vía `AskUserQuestion` el 2026-08-25 — repetidas acá por trazabilidad)

- Formato: 2 letras + 2 números + 2 letras (ej. "AB12CD").
- Campo **distinto** del código numérico de auto-check-in de T-20260825-004 — no se unifican.

## Decisión propia de esta sesión (no requirió pregunta al usuario, documentada acá por transparencia)

- **Unicidad por tenant, no global.** El nombre de columna (`db/schema/members.ts`) y el `uniqueIndex` la implementan como `(tenant_id, short_code)`, siguiendo el mismo patrón que `staff_members_user_id_unique` (unicidad simple, ahí sin tenant porque `userId` ya es 1:1 con una cuenta global de Auth) y, más directamente, `activities_tenant_id_name_unique` (unicidad compuesta con `tenant_id`, mismo caso de uso: un catálogo/identificador que solo tiene sentido "sin repetirse" dentro del mismo gym). Razón: toda consulta de este proyecto ya está scopeada por `tenant_id` vía RLS — el front desk de un gym nunca ve ni compara códigos de otro tenant, así que unicidad global no aporta ninguna garantía real de negocio y sí reduce innecesariamente el espacio de combinaciones disponible para un tenant grande (cadena con muchas sedes bajo un mismo tenant, por ejemplo). Si en el futuro se decide que el código debe ser escaneable/buscable cross-tenant (ej. un lector de código de barras compartido entre gyms de la misma franquicia), esta decisión habría que revisarla — no es el caso hoy.

## Por qué requiere revisión

- Es una migración de schema que **sí toca filas reales existentes** de `members` (a diferencia de una columna puramente aditiva sin backfill) — el bloque `DO $$ ... $$` hace un `UPDATE` por cada fila que hoy no tiene `short_code`. Por eso no se clasifica como `low` a pesar de ser un campo no sensible: hay backfill de datos reales, y ese es justamente el criterio que la tarea pedía usar para subir a `medium`.
- El backfill fue escrito a mano después de `drizzle-kit generate` (igual que en T-20260821-008 pass A) — mayor superficie de error humano que una migración 100% auto-generada, aunque la lógica es simple: recorrer filas con `short_code IS NULL`, generar un candidato, chequear colisión contra el mismo tenant, reintentar si choca, actualizar. Es idempotente en la práctica (el `WHERE short_code IS NULL` implícito en el `FOR` del bloque hace que una re-corrida sobre una tabla parcialmente backfillada solo toque las filas que aún no tienen código).
- A diferencia de T-20260821-008 (que necesitó dos passes porque había que backfillear un catálogo separado antes de poder apuntar la FK), acá el backfill y el `NOT NULL` final quedan en **un solo pass** — no hay tabla intermedia que poblar, cada fila recibe su propio valor random independiente. Señalarlo explícitamente por si la sesión orquestadora prefiere partirlo en dos gates de todos modos, dado el precedente.

## Verificación previa (lectura, no escritura) contra la base real

No se hizo una consulta explícita de "cuántas filas tiene `members` hoy" en esta sesión (a diferencia de T-20260821-008 pass A, que sí contó filas de `class_schedules` antes de escribir el backfill) — el bloque `DO $$` está escrito para funcionar correctamente sea cual sea el número de filas (incluyendo cero), así que no era estrictamente necesario para escribir la migración. Si la sesión orquestadora quiere ese dato antes de aprobar, se puede correr `SELECT count(*) FROM members;` contra `DATABASE_TRUSTED_URL` sin aplicar nada.

## Gaps conocidos, no resueltos en este pass

- **`npm run test:unit` no está limpio contra la base real hoy** — 8 de 34 tests fallan con `PostgresError: column "short_code" of relation "members" does not exist` (`SQLSTATE 42703`), porque la migración todavía no corrió contra la base real (correctamente, por proceso — no se corre `db:migrate` sin este gate aprobado). Es el mismo patrón exacto ya documentado en T-20260824-003 ("8 que fallaban antes de migrar por la columna inexistente, sin haber sido tocados") y en T-20260821-008 — se espera que estos 8 pasen a verde apenas se apruebe este gate y corra la migración, sin tocar el código de los tests otra vez. `npx tsc --noEmit` y `npx eslint .` sí están limpios (no dependen de la DB real).
- Sin verificación visual en navegador de los 3 lugares donde se agregó el display (`checkin-page`, `members-page`, `member-detail-page`) — requiere sesión real de owner/staff, igual que el resto de las tareas recientes de este proyecto.
- `features/members-page/components/member-form-dialog.tsx` **no se tocó** — el código corto es generado por el servidor, no un campo que el owner/staff completa al crear/editar un socio, así que deliberadamente no se agregó al formulario de alta/edición.
- No hay forma de **regenerar** un código corto desde la UI si alguna vez hiciera falta (ej. el owner quiere "resetear" el código de un socio) — no se pidió, no se construyó. Si se necesita a futuro, es un endpoint nuevo (`PATCH` puntual), no algo que este pass dejó a medio hacer.
- Sin RLS nueva que agregar — `members` ya tenía su policy `tenant_isolation` desde antes (T-001/T-002), esta columna no es una tabla nueva.
