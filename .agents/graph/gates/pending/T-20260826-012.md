## Decisiones ya confirmadas (antes de este `#run`, vía `AskUserQuestion`)

- Sin control de stock — catálogo simple, precio fijo, sin inventario.

## Qué se hizo

Schema nuevo:
- `products` (catálogo, sin stock, sin `deletedAt` — bloqueado de borrar si tiene ventas, vía FK restrict).
- `walk_in_sales` (append-only, unifica venta de producto y pase diario bajo un `kind` enum — `product` deriva el monto del catálogo server-side, `day_pass` lo tipea staff libremente, sin catálogo).
- `walk_in_sale_kind` enum (`product`/`day_pass`).
- RLS estándar (`db/policies/0009_products_walk_in_sales_rls.sql`).

API nueva: `GET/POST /api/v1/products`, `PATCH/DELETE /api/v1/products/[id]` (owner-only, pricing), `GET/POST /api/v1/walk-in-sales` (GET owner-only — dato de facturación; POST owner+staff — vender es operación de mostrador).

UI: pantalla nueva "Cobro rápido" (`/kiosk`, link agregado al nav para owner y staff) — grilla de productos con botón "Vender" de un tap, sección de pase diario (nombre opcional + monto libre), y (solo owner) "Ventas de hoy" + gestión del catálogo.

**`npm run db:generate` corrido — la migración `db/migrations/0015_stormy_moonstone.sql` está generada y revisada, pero `npm run db:migrate` NO se corrió contra la base real.**

## Por qué requiere revisión (síncrona, no async)

- Dos tablas nuevas + un enum — mismo criterio `high` que toda migración anterior de este proyecto. Aplicar contra la base real necesita aprobación explícita antes de `npm run db:migrate`.
- El monto de una venta de producto se deriva del precio **actual** del catálogo en el momento de la venta, no se snapshotea con un texto descriptivo — si el precio de un producto cambia después, las ventas viejas siguen mostrando el monto que efectivamente se cobró (correcto), pero el nombre que se ve en un join futuro es el nombre actual del producto, no el que tenía al momento de la venta. Aceptado como suficiente para esta primera vuelta (productos no se renombran seguido), señalado por transparencia.
- Decisión de scope propia: sin carrito/checkout de varios ítems en una sola venta — "pantalla rápida" pedía velocidad, no se pidió explícitamente un POS con carrito.
