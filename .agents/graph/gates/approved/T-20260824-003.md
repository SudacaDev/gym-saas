## Cambio de alcance respecto a como se registró la tarea

La tarea se había registrado con OAuth de Gmail (cuenta real conectada por
el owner). Durante la implementación se descubrió que el proyecto **ya
tiene Resend** integrado y funcionando hoy (`lib/email/resend-client.ts`,
usado por el recibo de pago en `app/api/v1/payments`) — se lo planteó al
usuario y confirmó reusar Resend en vez de construir un flujo OAuth
completo. Esto elimina toda la parte de `email_integrations` (token
storage, encriptación, conectar/desconectar) del alcance original: no hace
falta ninguna credencial nueva, el envío usa `RESEND_API_KEY`/
`RESEND_FROM_EMAIL`, ya configurados.

Decisión de producto confirmada con el usuario en la misma sesión: el
recordatorio automático se dispara **3 días antes** del vencimiento de la
cuota (`REMINDER_DAYS_BEFORE` en `lib/reminders/reminder-window.ts`).

## Qué se hizo

Ya se hizo, es local y no toca la base real (revertible con `git restore`/`git clean`):

- `db/schema/enums.ts` — `emailSendTypeEnum` (`reminder`/`manual`), `emailSendStatusEnum` (`sent`/`failed`).
- `db/schema/members.ts` — agrega `email_opt_out` (boolean, NOT NULL, default false) — gate de compliance: si es `true`, el cron automático nunca le manda nada a ese socio (los envíos manuales de staff no se ven afectados, es una decisión puntual de staff, no el barrido masivo que el opt-out existe para proteger).
- `db/schema/email-send-log.ts` — tabla nueva: auditoría de cada intento de envío (automático o manual), con `tenant_id` + RLS estándar. Unique index `(membership_id, reminder_scheduled_for)` como guarda de idempotencia para que el cron no mande el mismo recordatorio dos veces (NULLs no colisionan, así que los envíos manuales —que no llevan `reminder_scheduled_for`— nunca chocan entre sí ni con los automáticos).
- `db/schema/relations.ts` + `index.ts` — wiring de la tabla nueva.
- `db/policies/0005_email_send_log_rls.sql` — mismo patrón `ENABLE`/`FORCE ROW LEVEL SECURITY` + policy `tenant_isolation` que el resto.
- `db/migrations/0008_romantic_maginty.sql` — generado con `drizzle-kit generate` (sin conexión a la DB), puramente aditivo: dos `CREATE TYPE`, un `CREATE TABLE`, un `ALTER TABLE members ADD COLUMN`, FKs y el unique index. Nada destructivo, nada de backfill de datos (a diferencia de T-20260821-008 pass A).
- `lib/email/membership-reminder.ts` — builder + sender del mail (mismo patrón que `payment-receipt.ts`), copy en español, tono cordial y operativo, sin urgencia artificial.
- `lib/reminders/reminder-window.ts` — función pura `isDueForReminder` (ventana exacta de N días antes, no un rango) + constante `REMINDER_DAYS_BEFORE = 3`.
- `lib/reminders/send-and-log-reminder.ts` — orquesta envío + log, reusado por el cron y el envío manual (para que ambos caminos logueen siempre igual).
- `app/api/v1/memberships/[id]/send-reminder/route.ts` — POST, `requireRole(["owner","staff"])`, envío manual puntual.
- `app/api/cron/membership-reminders/route.ts` — GET, protegido por `CRON_SECRET` (no `getTenantContext`/`requireRole`, corre fuera de una sesión de usuario), recorre todos los tenants.
- `app/api/v1/email-send-log/route.ts` — GET `?memberId=...`, `requireRole(["owner","staff"])`, historial de intentos para la ficha del socio.
- `vercel.json` — cron diario a las 12:00 UTC (09:00 Argentina).
- `.env.local.example` — documentado `CRON_SECRET`.
- UI: `features/member-detail-page/index.tsx` — sección "Recordatorios" (botón "Enviar recordatorio" + tabla de historial), pill "No recibe automáticos" si `emailOptOut`. `features/members-page/components/member-form-dialog.tsx` — checkbox de opt-out. `app/api/v1/members/route.ts` + `[id]/route.ts` — persisten el campo.
- `tests/unit/membership-reminder.test.ts` — nuevo, pura lógica (sin DB): `isDueForReminder` (ventana exacta, no rango) y el builder del mail. **6/6 verde.**
- `npx tsc --noEmit` y `npm run lint` limpios en todo el proyecto.

## Por qué requiere revisión

- Es el primer paso hacia mandar mails automáticos a socios reales — aunque este gate específico solo crea schema (no envía nada todavía), es la puerta de entrada al resto de la tarea.
- Migración puramente aditiva (sin backfill, sin tocar filas existentes) — más simple que T-20260821-008, pero igual sigue la regla de oro: sin clasificación explícita en `policy.yml`, se trata como `high`.
- El cron en sí (`vercel.json` + `CRON_SECRET`) no envía ningún mail real hasta que el deploy tenga `CRON_SECRET` configurado y `RESEND_FROM_EMAIL` verificado — aprobar este gate NO activa envíos automáticos todavía, solo habilita el schema y el código. El primer envío real (cron corriendo en producción) amerita su propia confirmación cuando llegue ese momento.
