## Qué se hizo

Ya hecho, es local y no toca la base real (revertible con `git restore`/`git clean`):

- `db/schema/staff-attendance.ts` (nuevo) — tabla `staff_attendance`: `id`, `tenant_id` (FK a `tenants`, `cascade`), `staff_member_id` (FK a `staff_members.id`, no a `users.id` — mismo criterio que `staff_members`, es HR/schedule data), `clock_in` (timestamp, NOT NULL, default now()), `clock_out` (timestamp, nullable). Mismo patrón de "fila abierta que se cierra" que `db/schema/checkins.ts`'s `checkedOutAt`, confirmado explícitamente por el usuario como decisión #2 de esta tarea.
- `db/schema/relations.ts` / `db/schema/index.ts` — `staffAttendance` cableado: relación `many` desde `tenants` y `staffMembers`, `one` de vuelta hacia ambos.
- `db/policies/0007_staff_attendance_rls.sql` (nuevo) — `ENABLE`/`FORCE ROW LEVEL SECURITY` + policy `tenant_isolation`, mismo template exacto que `0006_staff_members_rls.sql`.
- `db/migrations/0013_old_paladin.sql` — generado con `npm run db:generate` (`drizzle-kit generate`, sin conexión a la DB). Puramente aditivo: `CREATE TABLE staff_attendance` + 2 FKs. Nada destructivo, nada de backfill (tabla nueva, no hay filas previas que migrar).
- `lib/validations/staff-attendance.schema.ts` (nuevo) — `staffAttendanceClockInSchema`: solo `staffMemberId` (uuid). No hace falta nada para el clock-out (el servidor resuelve la fila abierta desde los params de la URL).
- `app/api/v1/staff/[id]/attendance/route.ts` (nuevo):
  - `GET` — historial de fichajes de esa persona, más reciente primero (el "listado básico" pedido). Sin filtro `?open=true` como en `checkins`: el volumen esperado por persona es bajo (una fila por turno, no por visita), así que devolver el historial completo es barato.
  - `POST` — fichar entrada: inserta una fila nueva con `clock_out = NULL`. Rechaza con **409** si esa persona ya tiene una fila abierta (no permite doble fichaje de entrada) y con **404** si `staffMemberId` no existe o está dada de baja (`deletedAt IS NOT NULL`). El body solo necesita `staffMemberId` y debe coincidir con el `id` de la URL (chequeo de defensa en profundidad, no la fuente de verdad — la URL lo es).
- `app/api/v1/staff/[id]/attendance/[attendanceId]/route.ts` (nuevo) — `PATCH`: ficha la salida, setea `clock_out = now()` en esa fila puntual. El `WHERE` exige que la fila pertenezca a ese `staffMemberId` **y** siga abierta (`clock_out IS NULL`), así que un segundo click, una pestaña vieja, o un `attendanceId` de otra persona son un 404 sin efecto — nunca pisa una salida ya registrada ni cierra la fila de otra persona. Mismo criterio exacto que `PATCH /api/v1/checkins/[id]`.
- `app/api/v1/staff/route.ts` (`GET`) — se agregó `openAttendanceId` al SELECT: subquery correlacionada escalar (`SELECT id FROM staff_attendance WHERE staff_member_id = staff_members.id AND clock_out IS NULL LIMIT 1`) en vez de N llamadas a `GET /api/v1/staff/[id]/attendance` (una por fila renderizada) o un booleano simple — ver "Cómo se derivó el estado abierto/cerrado" abajo.
- UI en `features/staff-page/index.tsx`: botón de acción por fila que alterna "Fichar entrada"/"Fichar salida" según `openAttendanceId` (POST o PATCH directo, sin diálogo intermedio) + botón "Historial" que abre un diálogo nuevo (`features/staff-page/components/staff-attendance-dialog.tsx` + `.module.css`) con la lista de fichajes (fecha, hora entrada, hora salida o "En curso"). `handleSaved` (usado por `StaffFormDialog` al editar) se ajustó para preservar `openAttendanceId` localmente — la respuesta de `PATCH /api/v1/staff/[id]` no lo trae, así que sin este fix un simple "Editar" reseteaba visualmente el estado del fichaje.
- `features/staff-page/types.ts` — `StaffMemberRow` gana `openAttendanceId?: string | null`; nuevo `StaffAttendanceRow` (alias de `StaffAttendance`).

Falta ejecutar: `npm run db:migrate`. **No se corrió** en esta sesión.

## Decisiones tomadas — las dos más importantes de este gate

### 1. Sin pantalla de detalle de staff — diálogo por fila en vez de una ficha nueva

La decisión #3 confirmada con el usuario pedía "un listado básico de historial" ("ej. en la ficha de cada staff"), pero **hoy no existe ninguna página de detalle de staff** (a diferencia de socios, que tienen `features/member-detail-page/` + ruta `[memberId]`). Construir esa página nueva es un alcance bastante más grande que "básico" — una ruta nueva, un layout nuevo, navegación nueva.

**Se optó por la lectura más chica: un diálogo (`Dialog` ya usado en `StaffFormDialog`) disparado por un botón "Historial" en la misma fila de la tabla `features/staff-page/index.tsx`.** Muestra fecha + hora de entrada + hora de salida (o "En curso") de los fichajes de esa persona, más recientes primero. Si a futuro se necesita más (filtros por rango de fecha, exportar, editar un fichaje cargado mal), eso sí justifica una ficha de staff dedicada — pero no para esta primera vuelta.

### 2. Permisos: `owner+staff`, NO `owner`-only — la excepción explícita al endurecimiento de T-20260825-001

`app/api/v1/staff/route.ts` (el roster completo: nombre, DNI, contacto de emergencia, categoría) es **owner-only** desde T-20260825-001 — dato de RR.HH. restringido incluso para staff. La tentación natural era copiar ese mismo gate para el endpoint nuevo.

**Se decidió `owner+staff` para las 3 operaciones (`GET`/`POST`/`PATCH`) de `app/api/v1/staff/[id]/attendance/**`, no `owner`-only.** Por qué:

- La decisión #1 ya confirmada con el usuario para esta misma tarea dice textualmente: **"lo carga el owner **u otro staff** por él"** — es decir, el propio usuario ya estableció que un compañero de staff puede fichar la entrada/salida de otro. Restringir el endpoint a `owner`-only habría contradicho una decisión ya tomada, no habría sido "mi criterio", habría sido ignorar lo confirmado.
- Este sub-recurso expone únicamente timestamps de entrada/salida de **un** `staffMemberId` puntual — no expone DNI, contacto de emergencia, categoría, ni ningún otro campo del roster que T-20260825-001 restringió. La superficie de datos sensibles es distinta y mucho más chica.
- `GET` también queda `owner+staff` (no solo `POST`/`PATCH`) porque, si en el futuro se habilita una pantalla de front-desk para staff (hoy la pantalla "Equipo" completa solo la puede abrir el owner, ver el gap de alcance más abajo), esa pantalla va a necesitar poder leer `openAttendanceId`/el historial para decidir qué botón mostrar — dejarlo owner-only hoy solo pospondría el mismo trabajo, sin ganar seguridad real (el dato expuesto ya es de bajo riesgo).

**Gap de alcance relacionado, señalado para revisión:** en la práctica, hoy **solo el owner** puede llegar a estos endpoints, porque `app/(owner)/layout.tsx` ya redirige a cualquier usuario con rol `staff`/`member` fuera de todo el grupo de rutas `(owner)` — la pantalla "Equipo" (única superficie que llama a estos endpoints) vive ahí. Es decir: el gate de permisos a nivel de API es `owner+staff` como pide la decisión #1 del usuario, pero el gate de **routing** todavía no le da a staff ninguna pantalla desde la cual ejercerlo. Esto es exactamente el mismo gap que T-20260825-001 documentó para el presence widget — hardening a nivel de API, no cierre de un hueco activo. Si la intención real era que un compañero de staff pueda fichar a otro desde una pantalla propia (no la de "Equipo" completa, que sigue siendo owner-only), hace falta una tarea de UI/routing nueva.

## Cómo se derivó el estado abierto/cerrado por fila (sin N round-trips)

`GET /api/v1/staff` ahora selecciona `openAttendanceId` vía una subquery correlacionada escalar (no un booleano) — ver el bloque `sql` en el "Qué se hizo" arriba. Se eligió devolver el **id** de la fila abierta, no solo `true`/`false`, porque el botón "Fichar salida" necesita exactamente ese id para pegarle al `PATCH /api/v1/staff/[id]/attendance/[attendanceId]` sin un fetch intermedio en el momento del click — un booleano habría resuelto el label del botón pero no la acción en sí, obligando a un round-trip extra recién al hacer click.

## Por qué requiere revisión

- Toca datos reales de asistencia de cuentas de staff reales, cargados por un tercero (owner u otro staff) — mismo `severity_flag: medium` que el usuario ya adelantó en `tasks.md` al confirmar las decisiones de esta tarea.
- Tabla nueva con RLS nueva (`0007_staff_attendance_rls.sql`) — puramente aditiva, sin backfill (tabla vacía hoy).
- Cambia el permiso de un endpoint nuevo a `owner+staff` en un momento en el que el roster padre (`staff/route.ts`) fue explícitamente endurecido a `owner`-only hace apenas unas horas (T-20260825-001) — vale la pena que alguien confirme que la distinción "timestamps de fichaje" vs. "roster de RR.HH." es la línea correcta, no solo mi lectura.
- `GET /api/v1/staff` (endpoint ya existente, `owner`-only) gana una columna nueva (`openAttendanceId`) vía subquery — no cambia su gate de permisos, pero sí su forma de respuesta; cualquier consumidor que dependa de una forma estricta de esa respuesta debería revisarlo (no se encontró ninguno fuera de `features/staff-page/`).

## Gaps conocidos, no resueltos en este pass

- **Sin pantalla de detalle de staff** — ver decisión #1 arriba, es la lectura de alcance más chica, explícitamente documentada.
- **Solo el owner puede llegar a estos endpoints hoy en la práctica** (el routing de `(owner)/layout.tsx` no le da pantalla a staff), aunque el gate de la API es `owner+staff` — ver el gap de alcance dentro de la decisión #2 arriba.
- **Sin edición/corrección de un fichaje mal cargado** — no se pidió, no se construyó. Si un owner ficha una hora equivocada, hoy no hay forma de corregirla desde la UI (habría que ir directo a la base). Mismo tipo de gap que "no hay forma de regenerar `checkin_code`" en gates anteriores.
- **Sin límite de tamaño en el historial del diálogo** (`GET` devuelve todas las filas de esa persona) — aceptable al volumen esperado (una fila por turno), pero si con el tiempo alguien acumula miles de fichajes, esto debería paginarse. No se pidió para esta primera vuelta.
- **`npm run test:unit` no está limpio hoy, pero por una causa ambiental preexistente, no por este cambio**: 3-5 de 34 tests fallan en cada corrida (varía cuál) con `PostgresError: remaining connection slots are reserved for roles with the SUPERUSER attribute` / `sorry, too many clients already` — pool de conexiones saturado contra la base real, mismo síntoma ya documentado en el gate de T-20260825-002. Ninguno de los tests que fallan (`dashboard-metrics`, `checkin-checkout`, `payment-extends-membership`, `member-soft-delete`, `checkin-requires-active-membership`, según la corrida) importa ni ejercita código tocado por esta tarea — no hay ningún test de `staff_attendance` porque la tabla es nueva y vacía, no había insert existente que actualizar. `npx tsc --noEmit` y `npx eslint .` sí están limpios.
- **Sin extender `tests/integration/tenant-isolation/rls-policies.test.ts`** con un caso dedicado a `staff_attendance` — mismo gap ya señalado para `email_send_log`/`staff_members` en gates anteriores.
- Sin verificación visual en navegador — no es posible en este entorno (requiere sesión real de owner). No se afirma que se haya probado visualmente.
