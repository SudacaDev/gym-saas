## SQL que se aplicaría (`db/migrations/0006_quiet_bedlam.sql`)

```sql
CREATE TABLE "activities" (
	"id" uuid PRIMARY KEY DEFAULT gen_random_uuid() NOT NULL,
	"tenant_id" uuid NOT NULL,
	"name" text NOT NULL,
	"created_at" timestamp with time zone DEFAULT now() NOT NULL,
	"updated_at" timestamp with time zone DEFAULT now() NOT NULL
);
ALTER TABLE "class_schedules" ADD COLUMN "activity_id" uuid;
ALTER TABLE "activities" ADD CONSTRAINT "activities_tenant_id_tenants_id_fk" FOREIGN KEY ("tenant_id") REFERENCES "public"."tenants"("id") ON DELETE cascade ON UPDATE no action;
CREATE UNIQUE INDEX "activities_tenant_id_name_unique" ON "activities" USING btree ("tenant_id","name");
ALTER TABLE "class_schedules" ADD CONSTRAINT "class_schedules_activity_id_activities_id_fk" FOREIGN KEY ("activity_id") REFERENCES "public"."activities"("id") ON DELETE restrict ON UPDATE no action;

-- Backfill (agregado a mano, no generado por drizzle-kit):
INSERT INTO "activities" ("tenant_id", "name")
SELECT DISTINCT "tenant_id", "activity_name" FROM "class_schedules"
ON CONFLICT ("tenant_id", "name") DO NOTHING;

UPDATE "class_schedules" cs
SET "activity_id" = a."id"
FROM "activities" a
WHERE a."tenant_id" = cs."tenant_id" AND a."name" = cs."activity_name";
```

Más `db/policies/0004_activities_rls.sql`, aplicado por `scripts/apply-policies.ts` en el mismo comando.

## Por qué requiere revisión

- Migración de schema + **migración de datos reales** contra la base del proyecto — a diferencia de T-003/T-005 (puramente aditivas sin tocar filas existentes), acá hay un `INSERT ... SELECT DISTINCT` y un `UPDATE` que sí leen y escriben sobre las 6 filas de `class_schedules` que ya existen.
- El SQL de backfill fue escrito a mano, no generado por `drizzle-kit` — mayor superficie de error humano que una migración 100% auto-generada, aunque es SQL simple e idempotente en su lógica (el `ON CONFLICT DO NOTHING` la hace segura de re-correr).
- `activity_id` queda **nullable** después de este pass — la migración que lo hace `NOT NULL` y borra `activity_name` es un gate `high` separado (pass B), después de confirmar que el backfill corrió bien.

## Qué opciones se consideraron

1. **Una sola migración con rename automático de `activity_name` a `activity_id`.** Descartada: son tipos incompatibles (text vs uuid FK) — no es un rename real, y forzar a `drizzle-kit` a tratarlo como tal dispara su heurística interactiva de detección de rename, que no se puede responder en un script no interactivo.
2. **Dos pasos (elegida):** este pass agrega todo de forma aditiva + backfillea: la base queda en un estado intermedio válido (ambas columnas coexisten, `class_schedules` sigue funcionando igual que antes) hasta que un pass B separado, con su propio gate, complete la migración quitando `activity_name`.
