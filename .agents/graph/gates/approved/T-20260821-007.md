## Qué se hizo

Ya hecho, es local y no toca la base real (revertible con `git restore`/`git clean`):

- `db/schema/enums.ts` — `staffCategoryEnum` (`instructor`/`administrative`/`cleaning`), `staffDepartmentEnum` (`reception`/`sales`/`billing`/`management`), `staffShiftEnum` (`morning`/`afternoon`/`night`/`rotating`).
- `db/schema/staff-members.ts` — tabla nueva: `tenantId` FK, `userId` FK único a `users`, `staffCategory`, columnas nullable por categoría (`specialties` text[], `certifications`, `certificationExpiresAt` para instructor; `department` para administrativo; `shift` para limpieza), `dni`/`phone`/`hireDate`/contacto de emergencia comunes, soft delete vía `deletedAt` (mismo patrón que `members.ts`, no un boolean `active` como se había sugerido originalmente — se prefirió consistencia con la convención ya establecida en el código real).
- `db/schema/relations.ts` + `index.ts` — wiring de la tabla nueva.
- `db/policies/0006_staff_members_rls.sql` — mismo patrón `ENABLE`/`FORCE ROW LEVEL SECURITY` + policy `tenant_isolation` que el resto.
- `db/migrations/0009_cheerful_emma_frost.sql` — generado con `drizzle-kit generate` (sin conexión a la DB), puramente aditivo: 3 `CREATE TYPE`, 1 `CREATE TABLE`, 2 FKs, 1 unique index. Nada destructivo, nada de backfill.
- `lib/validations/staff-member.schema.ts` — `staffMemberSchema` (alta, con `superRefine` que exige `specialties` no vacío solo si `staffCategory === "instructor"`) y `staffMemberUpdateSchema` (edición, mismo shape sin `email` — el email es la identidad de la cuenta, no se edita desde acá).
- `app/api/v1/staff/route.ts` — `GET` (`owner`+`staff`, lista con join a `users` para nombre/email, filtra `deletedAt IS NULL`); `POST` (**owner-only**) crea la cuenta real: `admin.auth.admin.inviteUserByEmail` (la persona invitada fija su propia contraseña vía el mail que le llega — el owner nunca la maneja) y, si tiene éxito, inserta `users` + `staff_members` dentro de una transacción tenant-scoped. Si la transacción falla, se borra la cuenta de Supabase Auth recién creada (`admin.auth.admin.deleteUser`) para no dejar una cuenta huérfana sin fila de negocio — la compensación que pedía el plan original.
- `app/api/v1/staff/[id]/route.ts` — `PATCH` (**owner-only**, no toca `email`) y `DELETE` (**owner-only**, soft delete — nunca hard delete, por si horarios/clases referencian a la persona).
- `features/staff-page/` — pantalla "Equipo" (T-20260824-002): tabla (nombre, email, categoría, estado, fecha de alta, acciones), buscador cliente por nombre/email, diálogo `StaffFormDialog` (invitar/editar) con los campos comunes + sección condicional por categoría (chips de especialidad para instructor, reusando el patrón de `schedule-form-dialog.tsx`; `Select` de área/turno para administrativo/limpieza). Link "Equipo" agregado al sidebar (`owner-nav.tsx`, ícono `IdCardIcon`).
- `app/(owner)/staff/page.tsx` — ruta nueva.
- `npx tsc --noEmit`, `npx eslint .` y `npm run test:unit` (34/34) limpios.

Falta ejecutar: `npm run db:migrate`.

## Gaps conocidos, no resueltos en este pass

- **"Última conexión"** (pedida en la referencia de Linear para T-002) no se implementó — vive en `auth.users.last_sign_in_at`, una tabla de Supabase Auth que Drizzle no modela; traerla por fila implicaría N llamadas a la Admin API por request, algo frágil para una lista. Se dejó afuera en vez de construir eso a las apuradas; es un punto abierto para una iteración futura si el usuario lo pide explícitamente.
- **Revocar acceso real (desactivar la cuenta de Supabase Auth)** no está en el `DELETE` — el soft delete solo oculta el registro de RR.HH., no revoca el login. Señalado en el código (`app/api/v1/staff/[id]/route.ts`) como fuera de alcance de este pass.
- Sin verificación visual en navegador (requiere sesión real de owner). Sin extender `tests/integration/tenant-isolation/rls-policies.test.ts` para `staff_members` — mismo gap que quedó pendiente en T-20260824-003 para `email_send_log`.
- El primer alta real (clic en "Invitar" desde la app en producción) depende de que el envío de invitación de Supabase Auth esté configurado (SMTP propio o el de Supabase) — no verificado en esta sesión, es responsabilidad de configuración de infraestructura, no de este código.

## Por qué requiere revisión

- Migración de schema puramente aditiva (sin backfill, sin tocar filas existentes) — en principio más simple que T-20260821-008, pero la tabla que crea es la puerta de entrada a un flujo que sí crea cuentas reales de Supabase Auth. Sin clasificación explícita en `policy.yml`, se trata como `high` por la regla de oro.
- Aprobar este gate **NO crea ninguna cuenta real todavía** — solo habilita el schema y el código. El primer alta real ocurre recién cuando alguien con rol `owner` complete el formulario "Invitar" en la app corriendo de verdad; esta sesión no dispara eso.
