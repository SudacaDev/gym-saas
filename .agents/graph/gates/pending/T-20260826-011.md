# Gate: T-20260826-011 — Cupos y reservas de clases grupales

- severity: high (schema + migración nueva, mismo criterio que toda tabla nueva en este proyecto)
- approval_mode: sync
- created: 2026-08-26

## Scoping previo (no bloqueante, ya resuelto antes de escribir código)

La propia tarea pedía convocar `uiux-designer`+`backend-developer` antes de un `#run` directo — se hizo, en paralelo. Ambos convergieron sin coordinar entre sí:

1. **Cupo por ocurrencia real (fecha concreta), no por slot recurrente.** `class_schedules` no tiene concepto de fecha — la ocurrencia se deriva de `(class_schedule_id, date)` y se materializa recién en la primera escritura real (primera reserva), nunca por un job batch.
2. **Promoción de lista de espera manual, nunca automática por tiempo.** Automatizarlo necesitaría un cron frecuente que este proyecto no tiene (el único existe corre 1x/día) y resolvería un problema hipotético en vez del real (alguien parado en el mostrador, ahora).

La 3ra pregunta original de la tarea ("¿quién reserva?") no necesitó consulta — `PRODUCT.md` ya la resuelve: "members have no login to view them in-app", así que siempre es staff/owner desde el mostrador.

## Qué se hizo

Schema nuevo:
- `class_schedules.capacity` (integer nullable) — aforo default del slot.
- `class_occurrences` (tenant_id, class_schedule_id, date, capacity override nullable, unique por fecha).
- `class_reservations` (tenant_id, class_occurrence_id, member_id, status enum, created_at) — índice único **parcial** `(class_occurrence_id, member_id) WHERE status <> 'cancelled'`, permite recancelar/re-reservar.
- `reservation_status` enum: `reserved`/`waitlisted`/`attended`/`absent`/`cancelled`.
- RLS estándar (`db/policies/0008_class_occurrences_reservations_rls.sql`), mismo patrón que las 7 policies anteriores.

API nueva: `GET /api/v1/schedules/[id]/occurrences?date=`, `POST .../occurrences/reservations` (decide `reserved` vs `waitlisted` server-side según cupo efectivo), `PATCH .../occurrences/reservations/[reservationId]` (cambia estado y, si libera un cupo `reserved`, promueve atómicamente en la misma transacción la más antigua `waitlisted`).

UI: botón "Reservas" nuevo en cada slot de `ScheduleTableView` (solo esa vista) abre `ClassOccurrenceDialog` — fecha por defecto la próxima ocurrencia real, listas de reservados/espera/historial, buscador de socio para agregar. `ScheduleFormDialog` gana el campo de cupo default.

**`npm run db:generate` corrido — la migración `db/migrations/0014_lazy_scarlet_witch.sql` está generada y revisada, pero `npm run db:migrate` NO se corrió contra la base real.**

## Por qué requiere revisión (síncrona, no async)

- Dos tablas nuevas + un enum + una columna — el cambio de schema más grande de una sola tarea en lo que va del proyecto. Mismo criterio de severidad `high` que toda migración anterior (T-003/005/007, T-20260824-003, T-20260825-002/003/004): aplicar contra la base real necesita aprobación explícita de un aprobador nombrado antes de correr `npm run db:migrate`.
- Índice único **parcial** (`WHERE status <> 'cancelled'`) — primera vez que este proyecto usa esa forma de índice; generado y verificado en el SQL de la migración, pero vale una segunda mirada antes de aplicar.
- Decisión de scope propia, no preguntada de nuevo: la UI no expone el override de cupo por ocurrencia puntual (el schema sí lo soporta) — se dejó fuera para no inflar más el alcance de una tarea ya grande.
