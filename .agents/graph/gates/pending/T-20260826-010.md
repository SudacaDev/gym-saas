## Qué se hizo

Schema nuevo:
- `operational_requests` — `tenant_id` + RLS estándar, `reported_by_user_id` (FK a `users.id`, NOT NULL, `onDelete: "restrict"` — sigue el precedente de `emailSendLog.triggeredByUserId` para "quién hizo esto", pero obligatorio acá porque siempre hay un usuario autenticado detrás, a diferencia del cron de recordatorios), `description` (texto libre), `category` (enum opcional `supplies`/`maintenance`), `status` (enum `open`/`resolved`, default `open`).
- `operational_request_category` y `operational_request_status` enums nuevos en `db/schema/enums.ts`.
- RLS estándar (`db/policies/0011_operational_requests_rls.sql`, mismo patrón `tenant_isolation` que 0001-0010).

API nueva: `GET/POST /api/v1/operational-requests` (owner+staff), `PATCH /api/v1/operational-requests/[id]` (owner+staff, solo cambia `status` — no re-edita descripción/categoría).

UI: pantalla nueva "Necesidades" (`/operational-requests`, link agregado al nav para owner y staff) — listado con descripción, categoría, quién la reportó, fecha, estado (pill), y un botón que alterna abierto/resuelto; diálogo de carga simple (descripción + categoría opcional).

**`npm run db:generate` corrido — la migración quedó generada y revisada, pero `npm run db:migrate` NO se corrió contra la base real.**

## Por qué requiere revisión (síncrona, no async)

- Tabla nueva + dos enums — mismo criterio `high` que toda migración anterior de este proyecto. Aplicar contra la base real necesita aprobación explícita antes de `npm run db:migrate`.
- **Migración compartida con T-20260826-013 (Leads), corrida en paralelo en la misma sesión:** `drizzle-kit generate` detectó los schemas de ambas tareas a la vez (estaban en disco simultáneamente) y produjo un único archivo, `db/migrations/0016_soft_ender_wiggin.sql`, que crea `operational_requests` **y** `leads` (con sus tres enums) en la misma migración. No se puede separar limpiamente sin regenerar a mano — **este gate y el de T-20260826-013 terminan apuntando al mismo archivo de migración**. Si se aprueba uno sin el otro, `npm run db:migrate` de todos modos va a crear ambas tablas (no hay forma de aplicar la mitad de un archivo). Señalado por transparencia: lo más simple es aprobar ambos gates juntos antes de correr `db:migrate` una sola vez.
- Decisión de scope propia: `reportedByUserId` con `onDelete: "restrict"` en vez de `"cascade"` — este codebase no tiene ningún flujo de borrado real de `users` hoy (staff se borra soft vía `staff_members.deletedAt`, nunca la fila `users`), así que es un default conservador que no se espera ejercitar, elegido para no perder silenciosamente el historial de reportes si esa suposición cambia en el futuro.
- Decisión de scope propia: sin `DELETE` — no se pidió, y "abierto"/"resuelto" ya cubre el ciclo de vida completo pedido; un reporte cargado mal se puede simplemente marcar resuelto, no hace falta borrarlo.
- Decisión de scope propia: `PATCH` solo cambia `status`, no permite re-editar `description`/`category` — mismo criterio que `LeadFormDialog`/`ProductFormDialog` de otras tareas recientes: no se pidió edición del contenido original, solo el ciclo de vida.
- Sin restricción por `staffCategory`/`department` — la tarea confirmó explícitamente que el caso base es accesible para el rol `staff` en general; ese eje más fino es T-20260826-014, todavía no implementado.
- La vista propia del owner para estas necesidades queda explícitamente fuera de esta tarea (confirmado por el usuario, "más adelante").
