## Qué se hizo

Pantalla nueva "Mi perfil", reachable en `/profile`, staff-only (no `cleaning`):

- `lib/staff/resolve-own-staff-member.ts`: extendido de `{id, staffCategory}` a la fila completa (`username`/`phone`/`certifications`/`certificationExpiresAt`/`firstName`/`lastName`/`email`) — cambio compatible hacia atrás, T-007/T-008 solo usaban un subconjunto de esos campos.
- `app/api/v1/staff/me/route.ts` (nuevo): `GET` devuelve el perfil propio; `PATCH` acepta `phone` (todos) y `certifications`/`certificationExpiresAt` (solo si `staffCategory === "instructor"`, ignorado si no).
- `features/profile-page/**` (nuevo): 3 formularios — datos (PATCH al endpoint de arriba), contraseña y email (ambos hablan directo con `supabase.auth.updateUser()` desde el cliente, no pasan por nuestra API).
- `app/(owner)/profile/page.tsx` (nuevo): guard server-side, redirige a `/dashboard` si no es `staff` o si es `cleaning`.
- `app/(owner)/presence-widget.tsx`/`layout.tsx`/`owner-nav.tsx`: `PresenceUser` gana `category`; `NAV_LINKS` pasa de un booleano `ownerOnly` a una función `visible(user)` por link (necesario para expresar "staff, pero no cleaning"); agregado el link "Mi perfil".

## Por qué requiere revisión

- Primera vez que este proyecto deja que alguien cambie su propio email/password de Supabase Auth desde la UI — hasta ahora esas credenciales las definía siempre el owner al crear la cuenta (T-20260825-002).
- **Gap real, documentado en el código y no resuelto a propósito:** el cambio de email de Supabase no es inmediato — manda un link de confirmación. Este proyecto no tiene ruta `/auth/callback`; Supabase igual termina aplicando el cambio server-side una vez confirmado, pero la columna espejo local `users.email` (que hoy solo se escribe una vez, al crear la cuenta) no se resincroniza sola después. No se construyó un webhook/callback nuevo para cerrar ese gap sin que el usuario lo haya pedido explícitamente — señalado en vez de fingir que está resuelto.
- Refactor de `owner-nav.tsx`: `ownerOnly: boolean` → `visible(user): boolean` por link. Mecánico (mismo resultado para los 6 links existentes) pero toca la forma de `NAV_LINKS`, vale la pena una segunda mirada.
- "Clases" en el perfil de profesor NO es un editor nuevo — es un link a `/schedules`, donde el mismo acceso (owner+staff, sin distinción de categoría) ya existía. Decisión explícita para no duplicar `ScheduleFormDialog`.
